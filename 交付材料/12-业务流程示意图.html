图 5　业务流程与分支判定

一、主流程 12 步常态取数 → 判险 → 熔断 → 重算 → 三方案 → 人工决策 → 派单 → 叫应 → 回执 → 留痕

1

常态取数

RealWeatherService · ContestForecastService
  • 实况：CRA40 官方接口，缓存 10 min、每源 60 s、跨源 5 s、连败 3 次静默 300 s
  • 预报：GOWFS 未来 6h 累计降雨，独立 30 min（失败静默 600 s）
2

逐边判险

RouteService#buildRealRisk
  • 降水 ≥50mm/h→100、≥20→20；风 ≥60km/h→50、≥40→15
  • 能见度 <100m→50、<500m→20；高温 ≥35°C→8（冷链货损）
  • 台风 990hPa + 60km/h→100（判据只在 TyphoonRiskRule 定义一次）
3

熔断判定

DecisionSandboxService#applySection
  • penalty ≥ 100 即等效道路中断（IMPASSABLE_PENALTY）
  • 友谊关按企业档 80 / 100 / 120mm；芒街固定 70mm
  • 5mm 滞后：熔断后须降至 阈值−5 以下才恢复；≥50mm 只标"关注"不加惩罚
4

走廊重算

RouteService#shortestPath（A* 可采纳启发）
  • 熔断边在松弛阶段直接 continue 跳过 → 天然绕行
  • 全走廊搜不出：把硬熔断降级为软惩罚 50 再搜一次，并标 corridorAllFused
  • 兜底路线不当正常新线自动派单（见第 9 步 advisory）
5

三方案生成

SolutionAgent#buildPlans
  • A 公路绕行（真实路网重算）· B 陆水联运（平陆运河 LEGS）· C 原地等待（WAIT_HOURS=6h 货损模型）
  • 六维指标：额外耗时 / 全程耗时 / 风险 / 货损 / 油耗 / 费用 / 碳排，全部由引擎算出
6

AI 只写"为什么"

DeepseekService#chatWithChannel · RecommendationPool
  • 把算好的数字喂给模型，模型只产出推荐论述，不参与算数
  • 通道标注：本地 Ollama → 在线 DeepSeek → 历史文案池轮换 → 规则模板
  • 三智能体进度经 SSE agent-status 逐条点亮
7

人工决策

DecisionSandbox.vue · PlatformConfigurator.vue
  • 沙盘：7 要素滑块 / 真实降雨两档复算，改档即全链路重估
  • 企业模板（千企千面）：阈值档 + 货物 + 触达角色集
  • 调度员选定 routeChoice，决策权留在人这一侧
8

派单下发

POST /api/task/dispatch → TaskService
  • 建 TASK-n：货物/重量/温控/时限 + 选定路线快照 + AI 概率快照
  • registerActiveRoute 让守护中枢改盯这一单的起终点
  • SSE task-assigned 广播，大屏与司机端共用一条流
9

司机响应

/api/task/current · /accept · /reject
  • 司机端启动/刷新拉 /current 回到物流任务模式（断线重连不丢单）
  • 确认接单 → ACCEPTED；拒绝此单 → REJECTED 并退回普通导航，原因回流大屏供改派
10

分级叫应

OutreachService#dispatch(A|B|C)
  • 五类角色：调度员 / 司机 / 越方司机（越语）/ 船东船员 / 沿岸百姓 12 人
  • 黄·橙·红三档对应通道与确认方式；演示编排 4s / 4s / 3s 逐级回执
  • 未确认到点自动语音外呼，红色级再 +3s 把未确认名单上报调度端
11

在途守护

WeatherWatchdogService · RouteAgentService
  • 守护线程 60 s 巡检；风险变化入口 300 ms 防抖合并后异步重算
  • 逐条关注路线广播 route-update（advice + advisory + hazardEdgeIds）
  • 司机端约 30 s 上报进度，超 5 min 视为不在途（不用陈旧进度禁用方案）
12

留痕闭环

DecisionLogService
  • 10 类事件逐条落时间线：FUSE / UNFUSE / WEATHER / SANDBOX / AGENT / TASK / DISPATCH / CONFIRM / ESCALATE / CONFIG（实测 60 条）
  • 大屏「原始返回」可展开核对接口原文；恢复后回到第 1 步常态监控
↺ 第 12 步回到第 1 步：熔断 → 触达 → 回执 → 降雨回落 → 解除熔断 → 恢复通行 构成一次完整闭环，无人工干预也能自行收敛。

二、四条分支怎么走方向判定 DecisionSandboxService#direction()，推荐判定 SolutionAgent#recommend()

局势（direction）触发条件（代码原判据）推荐方案系统动作界面回显
normal 双线正常 公路未熔断 且 运河未禁航A（时效最优） 常态口径：六维给整趟绝对值而非"改道增量"，触达给派单前指令与权益保障 司机端顶部「全线通畅」；研判说"沿线口岸无生效熔断"，若别的口岸断了则点名"已熔断但不在本程路线上"
road_to_water 公路断 → 切水运 友谊关 fused 或被注入 penalty≥100 的等效熔断（暴雨 ≥80mm 或台风）B 陆水联运 方案 B 走平陆运河 LEGS（公路→换装→运河→海运），过闸费免征、碳排按水运系数 0.35；装船时刻取 DemoClock.boarding() 真实时钟，不写死 15:30 沙盘断面「友谊关 120mm 已熔断 · 降雨量需降至 75mm 以下才恢复通行」；推荐语给"赶时效走公路 / 省成本走联运 9 小时"取舍
water_to_road 水运禁航 → 切公路 能见度 <1000m 或 设计流速 >2.0m/s 或 有效浪高 >2.0m 或 风速 ≥13.9m/s（7 级）——任一即禁航A 公路 方案 B 降级为「禁航·锚泊等待」（+8h 与锚泊费），软惩罚 WATER_FUSE_PENALTY=100 抬高成本而非删除；状态翻转即广播 canal-block / canal-recover，携带受影响运河路线清单 运河断面「平陆运河 已禁航」＋红线原因（含"由风速推算""含支流涨水联动贡献"）
dual_risk 双线风险 公路熔断 且 运河禁航C 原地等待 等待 6h 后复判；货损率按货物延误敏感度模型算（冷链火龙果 6h 满档），强行通行货损与安全均不可控 推荐语直说"公路与水运双线风险叠加"，不给虚假的绕行希望
corridorAllFused 全域受阻 公路所有走廊都搜不出（含降级兜底仍无路）且 运河禁航 —— CorridorAdvisoryService C（形态按局势变形） 三选一动作：DEFER 未发车→暂缓发车；RETURN 在途未过口岸→按真实路网给折返里程与耗时；HOLD 已出境→折返要重新通关不经济，建议就近安全停靠。出境点位置以 customsCrossRatio 下发，司机端用本地 GPS 进度自行复算动作 方案 C 卡标题改写为「返回起点待命 / 就近安全停靠等待 / 暂缓发车待命」；等待时长注明"无预计解除时刻的预报数据，到点复判，不作为承诺时效"
进度闸门 横切分支 progressRatio > BACKWARD_GATE(0.5)B 置为不可用 车已开过装货港（南宁港六景）→ 方案 B 标 notApplicable，不进六维表、不参与推荐；此时公路断则退而求其次 A → C。在途行程也不读预生成缓存（缓存不包含车辆当前位置） 方案 B 卡显示"车辆已行驶全程 X%，装货港已在身后，回港口换乘不经济——本方案对当前行程不适用"

三、在途实时链路一条 SSE 流承载五类事件，大屏与司机端同源

触发源

守护线程 60s 巡检 / 沙盘改档 / 官方推送 / 灾害注入 / 支流实况联动，全部走同一入口 notifyRiskChanged(reason)

防抖合并

300ms 窗口内的多次风险变化合并为一次重算，异步线程执行，界面不卡；重算失败也照发（附 error 与兜底建议）

逐条关注路线重算

关注集合含：导航中 / 已选线未开始 / 目的地越南端 / 大屏兜底主路线；每条单独出 planRouteFast 结果

SSE 广播

route-update（advice＋advisory＋hazardEdgeIds）、task-assigned、agent-status、outreach-update、canal-block/canal-recover

两端各自过滤

payload 带 origin/destination，大屏与司机端只处理自己的路线；芒街熔断而本程走友谊关时，司机端不会被骚扰（"另一走廊有 N 处风险，不在当前路线上"）

四、断网与降级链路断网时全链路仍要能跑，且降级必须被说出来

气象数据
  1. 主CRA40 官方实况 + GOWFS 官方预报（ContestWeatherProvider）
  2. 降Open-Meteo 备源；命中缓存直接回旧值并标 servedFresh
  3. 底SimulatedWeatherProvider 离线模拟温和天气，卡片有数且不误报灾害
  4. 标界面「实时 / 模拟降级」徽标 + /api/weather/source 可查真正来源
AI 文案
  1. 主本地 Ollama（数据不出境，优先级最高）
  2. 降在线 DeepSeek（提示词离开本机 → 标签写「在线 API · 非本地」）
  3. 底历史 AI 文案池按情境签名轮换取用，最后一层落规则模板
  4. 标通道标签只有 本地 / 在线 / 缓存 / 模板 四种原文；三智能体取"最远程"的通道汇总标注
决策结果
  1. 主三智能体串行现算（研判→方案→触达）
  2. 降预生成缓存 decision-cache/scenario_*.json，2 秒出结果并标 cacheHit
  3. 底路线与方案数字本就不依赖模型：本地路网 A* 现算，断网照样出真值
  4. 标旧缓存里写死的"本地大模型"字样一律降为「预生成文案（生成时未记录真实通道）」
底图与路网
  1. 主天地图影像/矢量（密钥池轮转 + per-key 熔断 + 内存/磁盘两级缓存）
  2. 降OSM → 包内离线瓦片 data/tile-cache，底图 1~4 手动可切
  3. 底算路用本地路网（约 8.6 万节点 / 9.8 万边），不依赖任何外部算路 API
  4. 标顶栏「OSM 状态 / OSM 未加载」标出加载器开关，公网演示形态直接封死该入口
任务与触达态
  1. 主SSE 实时推送派单与叫应状态灯
  2. 降SSE 断开 → 司机端启动/刷新 GET /api/task/current 回到物流任务模式
  3. 底叫应超时升级由后端定时器驱动，不依赖前端在不在页面上
  4. 标触达面板逐角色「已送达 / 已确认 / 外呼中」＋已确认 n/n 计数

五、界面证据上述分支与降级在真实界面上都有对应回显

读图要点三条： ① 数值与文字分家——时效、里程、成本、货损、碳排全部由确定性引擎算出，大模型只写"为什么推荐"，数值链路不依赖模型与网络； ② 分支只由两个布尔量决定——roadBlocked 与 waterBlocked（外加进度闸门与全域受阻判据），沙盘滑块调档即可复现任一分支； ③ 降级层都有原文标签——每一层兜底在界面上标为「模拟降级 / 在线 API / 预生成文案」，来源与通道随状态显示。 配套：图 3 服务蓝图（《10》）看角色接触点，图 4 界面原型（《11》）看这些判定的落点界面，图 1/2 系统架构（《08》《09》）看模块归属。
